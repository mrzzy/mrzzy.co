# Introduction

<video controls src="/videos/projects/borche/demo.mp4"></video>

As part of my Final Year Project, I developed **Broche**, an iPad AI-Assisted Drawing App designed to explore how generative AI can augment rather than replace artists.

Several engineering challenges encountered during the development process is discussed here:
- AI Model Deployment
- Performance Optimisation
- AI Agent Design

Source code for the project is available on [GitHub](https://github.com/mrzzy/ntu-fyp).

## AI Model Deployment

One of the earliest architectural decisions was whether AI inference should be performed **offline on the iPad** or **online through external inference providers**.

### Offline Deployment

Running models locally offers several attractive properties:

- No network connection is required for inference.
- User data remains on-device.
- There are no per-request inference costs.
- The application does not depend on external inference providers.

I initially explored on-device inference runtimes including MLX, UZU and LiteRT-LM for language models, as well as Core ML Stable Diffusion and Media Generation Kit for image generation.

However, the iPad's resource constraints made a fully offline architecture impractical for the target application.

The primary limitations were:

- **Model support**: UZU performed well in our benchmark but lacked the VLM support required for sketch understanding.
- **Image quality**: the available quantised Stable Diffusion deployment produced insufficient image quality.
- **Feature support**: Media Generation Kit supported Flux.2 text-to-image generation but failed when supplied with an image prompt, which was essential to the application's workflow.
- **Model loading**: model weights had to be distributed separately due to the iOS application bundle size restriction, introducing significant download and model-loading delays.
- **Memory utilisation**: large models consumed a substantial portion of the iPad's unified memory. Loading the 4B-parameter Qwen 3.5 VLM consumed approximately 5.2 GB of an 8 GB memory budget.
- **Model capability**: resource constraints limited the application to smaller and weaker models and restricted the ability to load multiple models simultaneously.
- **Dependency complexity**: integrating multiple on-device inference frameworks introduced build-time dependency conflicts.

Offline deployment therefore offered better privacy and independence, but at the cost of model capability, memory, loading time and implementation complexity.

### Online Deployment

Online inference moves model inference to external servers. This substantially relaxes the application's compute and memory constraints and provides access to larger, more capable models.

The main advantages were:

- Access to state-of-the-art models.
- No model download or model loading delay on the device.
- Minimal local resource utilisation.
- No need to bundle large model weights and inference dependencies.

The trade-offs were **inference cost** and **API key security**.

Online deployment was ultimately selected because its higher resource limits made the application's multi-model architecture practical, while warm inference avoided the long model download and loading process associated with offline deployment.

2 Online inference providers where use to perform model inference for the app:

- **OpenRouter** for LLM and VLM inference.
- **Replicate** for diffusion model inference.

#### Securing API Key Credentials

I evaluated several approaches for securing inference credentials:

![CloudKit Database](/images/projects/broche/apikey_cloudkit.png)

- **CloudKit Database** This architecture offloads the API Key to the public CloudKit Database. Before making an Inference Request to an AI Inference API, it first fetches the long-lived API Key from the Database, then contacts the Inference Provider’s API directly to make the AI Inference Request.

![Authenticated User with Proxy](/images/projects/broche/apikey_cloudkit.png)

- **Authenticated User with Proxy** This design restricts access to authenticated users only. Using Firebase Authentication, users must authenticate before using the Broche App. The API Key is never disclosed to the client App. Instead, the App may only make requests indirectly via a backend proxy server, which is responsible for relaying the Inference request to the actual Inference Provider.

![Authenticated User with Database](/images/projects/broche/apikey_db.png)

- **Authenticated User with Database** Again, users are forced to authenticate before using AI features. Authenticated users are given direct access to the Inference API by fetching a record containing the long-lived API Key in the Firestore Database.

![Authenticated User with Database and Key Rotation](/images/projects/broche/apikey_db_rotate.png)

- **Authenticated User with Database and Key Rotation** Extends the design by the addition of Firebase Function that periodically rotates API keys stored in the Firestore Database. The job contacts the AI Inference providers to issue fresh API keys and subsequently writes to the Firestore Database. The App obtains the rotated API Keys from the database prior to making a request to an inference provider, ensuring that it always uses the latest API key for authentication.

## Performance Benchmarking

![Lag Panning and Zooming](/images/projects/broche/lag.gif)

Acceptance testing identified two major performance problems in the Sketch View:

1. **Drawing Stroke**: individual drawing strokes could take several seconds to register and render.
2. **Panning and Zooming**: manipulating drawings containing AI-generated image layers introduced noticeable rendering latency.

Xcode's Instruments Time Profiler was used to identify the dominant execution paths.

### Drawing Stroke

![Profiler Image Getter](/images/projects/broche/profiler_image.png)

Profiling showed that a significant amount of execution time was spent in `Sketch.image.getter`.

The problem was caused by the Sketch selection sidebar. SwiftUI refreshed the sidebar when the drawing changed, causing the drawing image to be rendered again even though the rendered image itself had not meaningfully changed.

The optimisation was therefore straightforward: **cache the rendered drawing image** rather than reconstructing it on every view refresh.

The cache expires after five seconds to ensure that the displayed preview is eventually refreshed.

### Panning and Zooming

![Profiler Render Layers](/images/projects/broche/profiler_layer.png)

Profiling also showed that `SketchRender.renderLayers` dominated execution time during panning and zooming.

The original implementation recombined every drawing layer whenever the viewport changed. However, during normal drawing interactions, only the top layer is actively modified.

An optimised rendering strategy was introduced:

- Render the lower, relatively static layers once.
- Cache the resulting image.
- Re-render only the top layer during interactive manipulation.
- Composite the cached lower layers with the dynamic top layer.

This avoids repeatedly performing expensive rendering work that cannot affect the current interaction.

## Agent Design

![Profiler Render Layers](/images/projects/broche/sketch_agent.png)

The Sketch Agent provides the conversational interface between the artist and the application's AI features.
Users text naturally with the Sketch Agent, which invoke tools that act on the user's Sketch. This provides a friendlier entrypoint to AI feature for users unfamiliar with the intricacies of Diffusion Models.

The agent has access to several tools:

- `caption_sketch` - understands the current drawing using a VLM.
- `explain_edit` - interprets the user's intended edit.
- `edit_sketch` - performs an incremental image edit.
- `render_sketch` - transforms a sketch into a polished image.
- `list_mood` - discovers user-created moods.
- `inject_mood` - retrieves the description associated with a selected mood.

Underneath the hood, the agent itself powered by **Qwen3-30B-A3B-Instruct-2507** LLM.
It has access to tools powered by **GPT 5 Nano** VLM and **FLUX.2 Klein 9B** Image Generation models.

### Static Workflow Guidance

A key implementation finding was that simply providing the LLM with a collection of tools was insufficient.

Without additional guidance, the agent's tool selection was unreliable.

The system prompt provides static procedural guidance describing which tools should be invoked for each type of user request:
```
You are a sketch assistant. Help users render or edit their sketches and
provide visual guidance.
...
You may use tools to complete tasks.

If the user specifies a mood or style, use (ListMoodTool.NAME) to list
available moods, then (InjectMoodTool.NAME) with the mood's id to retrieve
its full description.

1. Rendering Pipeline:
   [(CaptionTool.NAME), (ListMoodTool.NAME), (InjectMoodTool.NAME),
   (RenderTool.NAME)].
   Use when the user wants to render a final image.

2. Editing Pipeline:
   [(ExplainEditTool.NAME), (ListMoodTool.NAME), (InjectMoodTool.NAME),
   (EditTool.NAME)].
   Use when the user wants to modify or refine the sketch.

Do not use both (EditTool.NAME) and (RenderTool.NAME) for the same user
message. Choose one pipeline based on the user's request.
```
